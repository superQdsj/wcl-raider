# 数据口径与 WCL API 备忘

读数据前先确认口径，避免把"统计方式"误判成"玩家问题"。

## 检查 → 数据 → 补查 → 无法观测
| 要检查的事 | 直接数据 | 补查方法 | 日志无法证明的部分 |
|---|---|---|---|
| 死前发生了什么 | `deaths` 逐次详情（血线、承伤、治疗、施法、增益） | `events --from --to --player <死者> --type all`（双向：施放或承受） | 视野、距离、语音沟通 |
| 自保当时是否可用 | `deaths` 的技能可用性表 | `player <玩家> --ability <技能>` 查全部施放时间 | 天赋/装备导致的冷却变化、充能、重置；没带的消耗品 |
| 减伤是否覆盖 | 死前获得的增益 | `events --type buffs --player <玩家> --from --to`（看 applybuff/removebuff） | 进入窗口前就有、窗口里没有刷新的增益要往前查 |
| 某人在哪儿被打中、停留多久 | `damage --ability <技能>` 的受伤段 | `events --type damage-taken --player <玩家> --ability <技能>` | 精确站位（原始事件带坐标，但工具不展示，一般不做站位分析） |
| 死后缺席多久 | `deaths` 的"回归"列（上界） | `events --from <死亡> --to <+90s> --player <死者> --type casts --limit 3` | 非常规复活方式 |
| 打断容量够不够 | `interrupts --pull N` | `events --pull N --type enemy-casts`、`--type interrupts` | 语音分工、谁被分配了哪只怪 |
| 读条是否引发了死亡 | `deaths` + `interrupts` 的读完时间点 | `events --type enemy-casts --from <死前30秒> --to <死亡>` | 读条、减益、伤害的 ID 常常不同，要按名称和时间先后对应 |
| 治疗蓝量 | 无 | `query` 查资源事件（见文末） | — |
| 锁定/点名 | 无 | `events --type debuffs --player <受害者>` | 未在日志中表现为减益的机制 |

## 时间
- 所有命令里的 `m:ss` 都是**相对钥石开始**的 WCL 时间（WCL 的战斗开始 = 插入钥石那一刻）。
- **游戏内计时 ≈ WCL 时间 − 10 秒开场倒计时 + 此前累计的死亡罚时**。只在还没有人死亡时，两者才近似相差 10 秒。给队伍的建议优先引用波次和读条信号，不用绝对时间。
- `官方用时` = keystoneTime，即暴雪排行榜成绩，**已包含死亡罚时**。`实际时长` = 记录的真实时长，包含开场倒计时，不含罚时。`扣除罚时后的用时` = 官方用时 − 罚时合计，拿它和高分比，可以分清"问题在死亡"还是"问题在节奏"。
- 罚时由工具反推：每次死亡罚时 = (官方用时 − (实际时长 − 10 秒)) ÷ 死亡次数，结果取整到 5 秒。午夜 S2 实测（各层 8–10 场带死亡记录）：**+2–+5 不罚时**（带 165 号词缀），**+6–+11 每次 5 秒**，**+12 起每次 15 秒**（147 号词缀"萨拉塔斯的狡诈"）。没有官方用时（未完成）时，按这个规则推断，并标明依据。
- +2/+3 档位线 = 限时的 80%/60%，和 WCL 的奖励数据一致。限时来自 Raider.IO 静态数据，取不到时会注明。

## 波次（pulls）
- 一波 = WCL 自动切分的连续战斗段（dungeonPulls）。几波怪连在一起拉、中间不脱战，会被合并成一波。只有 0.1 秒的伪波次会被忽略。
- "进度" = 该波被击杀怪物的进度值合计（击杀事件 × 每种怪的进度值），各波相加 ≈ 官方进度。
- "团队DPS/承伤每秒"来自 WCL graph（约 7 秒一个采样点）按波次窗口积分，只适合比较波与波的相对强度。
- 首领战：encounterID > 0 的波次。kill=false 表示该次首领战没有击杀（灭团或重置）。
- "嗜血"列：该波内出现嗜血/英勇/时间扭曲/原始狂怒、唤魔师与战鼓等团队急速增益的时间（同一次施放给全队上的增益合并为一次）。汇总里列出每次的施放者。

## 死亡（deaths）
- 只统计玩家死亡（不含宠物/图腾）。"串"是把相邻间隔 ≤20 秒的死亡归为一组。一组里倒下的不同玩家 ≥ max(3, 在场人数−1)（在场人数最多按 5 人计）时，标为"疑似团灭"。**串首只是起因候选**，分组只看时间间隔，不代表因果。
- 先检查完整性：死亡总数与展开的编号是否一致。输出被截断时（会有提示），用 `--detail N`、`--max-chars 0` 或 `events` 分段补查。
- 逐次详情的时间是**相对死亡时刻**（-3.2s = 死前 3.2 秒）。`剩x%` 是该次伤害之后的血量。"死前承伤"含被护盾吸收的部分；"相当于最大生命的 N%"超过 100% 很正常，说明期间也有治疗。
- "获得的增益"包含大量触发效果（饰品、天赋、光环），需要自己分辨哪些是减伤或外部技能。窗口之前获得、仍在持续的增益不在这里，要用 `events --type buffs` 往前查。
- "施法"不含普攻。
- **技能可用性表**：列出死者本场用过、频率不高的技能，以及死前最近一次使用距死亡的时间、本场两次使用之间的最短间隔、判定。判定"可用" = 距上次使用 ≥ 最短间隔（最短间隔不会短于冷却）；"可能在冷却" = 距上次使用 < 最短间隔；只用过一次或死前没用过 = 无法判定。**充能类技能不适用这条规则。**
- **"复活"列**：死亡后、该玩家下一次死亡之前的第一次 resurrect 事件（战复、灵魂石等）。它可能漏掉非常规复活，所以"未战复"不代表一直缺席。
- **"回归"列**：死后 300 秒内第一次主动施法或给自己上增益的时间，是缺席时长的**上界**。估算缺席以它为准，不要默认缺席到该波结束。
- 战复充能工具不显示，写成"充能未核实"。

## 打断（interrupts）
- 表中只有**至少被打断过 1 次**的敌方技能。从没被打断过的可打断技能看不到，要用 `compare` 看高分队伍断了哪些。
- 读条 = 开始施法次数；打断 = 被打断（含引导被打断）；读完 = 施放成功；其他中止 = 读条 − 打断 − 读完（被控制、施法者死亡、目标丢失等）。
- **"计数"列标"不一致"**（打断 > 读条，或打断 + 读完 > 读条 × 1.05）时，这一行的打断率不可靠，不要据此下结论。
- 每人打断分成两列：**纯打断**（脚踢、拳击、风剪、心灵冰冻、反制等打断技能，加上复仇之盾）和**控制打断**（击倒、恐惧、致盲等被 WCL 计为打断的效果）。控制一次可以"打断"多只怪，不能和纯打断按次数等同。
- "施放−打断计数" = 纯打断技能的施放次数减去成功次数，按同名合并。它是汇总差值，不等于空断次数。
- 漏断时间点按波次汇总（如 `#7×20`）。漏断集中在某一波时，用 `interrupts --pull N` 看该波的容量：读条次数、施法者数量、每人的打断施放与最短间隔（冷却的上界），以及估算的可用打断次数。这只是估算。

## 驱散（interrupts 命令末尾）
- 来自 WCL 驱散表（结构与打断表相同）：出现 = 该效果被施加的次数，被驱散 = 被驱散的次数，未驱散 = 自然结束或一直没被驱散的次数，并附驱散者、驱散技能、被驱散的对象和"未驱散"的时间点。
- 只有被驱散过至少 1 次的效果才会出现。从没被驱散过的可驱散减益看不到，需要用 `events --type debuffs` 自己查。也会包含对敌方的驱散（进攻驱散、偷取），从"被驱散对象"能看出来。

## 承伤（damage）
- 默认不含近战（近战主要由坦克承受，单独汇总一行）。
- "敌方施放"（uses）是敌人施放该技能的次数，并非所有技能都有，例如地面效果没有。"每次施放命中" = 命中 ÷ 敌方施放，是**事件比值，不等于中招人数**。它只对"一次施放打中少数人"的技能有意义；光环和持续型技能一次施放会反复命中，要按战斗时长比较。
- "命中/跳"：命中 = 直接伤害次数，跳 = 周期伤害次数。
- 分布标记（与工具输出一致）：`仅坦克` 或 `坦克占N%`（坦克承受为主）、`全员承伤接近`（≥4 人且最大/最小 ≤3 倍）、`集中:某人N%`（非坦克个人占比 ≥35% 且 ≥ 中位数 2 倍）、`只打中:某人`。这些只描述"谁在承受"，**不等于可躲/不可躲**。
- 来源为"环境"的伤害通常是地面效果或场景机制。
- `damage --ability <ID或名称>`：每人在每一波被打中几次，以及"受伤段"。受伤段把相邻 ≤2.5 秒的命中合并成一段，可以看出在地面效果里停留了多久。

## 输出与百分位（overview / player / spec）
- DPS/HPS 按整场实际时长计算（与 WCL 一致），所以死亡、跑路、脱战都会拉低数值。
- 同层百分位 = WCL 上同副本、同层数、同专精的排名百分位（治疗按 HPS，其余按 DPS）。**旁边会显示同层样本量**：高层（例如 +24）同专精可能只有 4–7 人，这时百分位噪声很大，标为"不可靠"。括号里的总百分位不分层数，参考价值较低。
- **活跃时间是 WCL 伤害表的 activeTime ÷ 整场时长，不是 GCD 利用率**。不同专精之间差异很大（同专精顶尖也可能只有 70–80%），不能单独用来判断"停手"，只适合和同专精顶尖比较（`spec`）。
- CPM = 每分钟战斗时间的施放次数（按战斗中时长计算）。`spec` 对比时，双方都按各自的战斗中时长计算。
- 低频技能时间轴：CPM ≤ 1.2 的技能，多为爆发、减伤、位移、功能或消耗品。"最短间隔"接近冷却 = 基本按 CD 在用；"首领战是否使用"可以看出大招和减伤有没有交在关键战斗。其他技能用 `player --ability`。
- 药水/治疗石次数来自 WCL 的 potionUse/healthstoneUse，只有次数，没有时间点。

## 分段计时（splits）
- **一段** = 从上一个首领击杀（或钥石开始）到下一个首领击杀，包含段里的小怪、首领战、失败尝试和脱战。最后一个首领之后还有记录时，算作"收尾"。两边按首领（encounterID）对齐；首领顺序和本场不同的参考会被标出，并且排在后面。
- 时间是**实际经过的时间**（WCL 计时，含开场 10 秒倒计时），不含死亡罚时。罚时在表下单独列出。
- **参考记录**：默认从 WCL 同层排名里取前几页带日志的记录（`--candidates`，默认 8 条），只选完成的钥石，按"首领顺序一致 → 路线相似度 → 用时"挑出 `--refs` 条（默认 3）。`--ref <链接或 CODE#fight>` 可以指定参考，例如自己上一把限时的记录；只给报告代码时，自动选该报告里同副本最后一条完成的钥石。
- **路线相似度**：全场"给进度的小怪"构成的加权重合度（权重 = 每只怪的进度值）。不给进度的召唤物、首领机制刷出的小怪不参与。它只看拉了哪些怪，不看拉的顺序和合拉方式。
- **怪物去重**：同一只怪（gameID + 实例编号）跨两波出现，只算在第一次出现的那一波。灭团后重拉的怪也算"之前出现过"，所以在波次对照里，这样的波次参考估计为 0，整波都是多花的时间。实例编号是 WCL 按出现顺序分配的，个别情况下（例如怪物重生后换了编号）可能去不干净。
- **段内进度**按该段出现的怪（去重后）× 进度值计算，各段之和可能与官方进度相差几个百分点（出现了但没被杀死的怪也算进去了）。
- **按节奏折算超额** = 本段用时 − 参考本段用时 × (本场总时长 ÷ 参考总时长)，取各参考的中位数。它把"参考整体更快"（装等、阵容）按比例扣掉，剩下的是本场在这一段特别慢（正）或特别快（负）的部分。各段超额之和约等于 0。
- **波次对照**：在参考的同一段里，把每一波小怪的战斗时间按进度比例分给波里的每只怪，得到"每种怪平均耗时"；再按本场这一波拉的怪加总，就是"参考拉同样这些怪大约要多久"。参考拆拉、合拉都能比较。它只算战斗时间，不算波与波之间的脱战；覆盖率 < 50% 时不比较。首领那一行直接比较击杀那次首领战的用时。
- **成本**：每条候选记录约 1–3 点（首次），之后走 7 天缓存。

## 险情（danger）
- 数据：`includeResources` 的承伤和治疗事件里，承受者在这次事件之后的血量（`hitPoints/maxHitPoints`，只取 `resourceActor = 2` 的事件）。不含护盾，因此带大护盾的人看起来会比实际更危险。
- **个人险情**：血量跌破阈值（默认 35%），到回到 50% 以上为一次；回到 50% 后 3 秒内又跌破，算同一次。跌破后 8 秒内死亡的算"低血后死亡"，不列入险情（死亡看 `deaths`）。
- **团队险情**：4 秒内至少 3 人同时低于 50%（队伍少于 5 人时降为 2 人），相邻 15 秒内的合并为一次。
- "前 6 秒伤害构成"是跌到最低点之前 6 秒内该玩家承受的伤害（含被吸收的部分），按技能占比列出。它告诉你是什么打的，但不说明躲不躲得掉（见 playbook §4.3）。
- 持续时间按事件计算，误差约为相邻两次受击/受治疗的间隔。
- 成本：整场承伤 + 治疗事件，通常 3–6 点。

## 对比（compare / spec）
- 基准是 WCL 该副本同层（不足时扩大到全部层数）排名靠前的带日志记录，已排除本场。记下样本数、对方阵容和层数。前排可能是同一支队伍的多场记录；低层前排往往是装等远高于本队的速通。
- 跨层时，伤害数值不可比；命中次数、每次施放命中、打断率、CPM、用时结构，在机制一致时可比。
- "只在本场出现的承伤技能"可能是路线不同（对方没拉那只怪），也可能对方完全躲开了，需要结合怪物构成判断。
- 高分队伍也不怎么打断的技能，通常优先级低。

## 评分（score）
- 公式、权重和 `judgments.json` 的格式见 `scoring.md`。默认拉取与 `compare` 相同的 3 场同层高分记录（有缓存则不耗点数）。`--no-compare` 时，关键打断为 N/A。
- "暴露偏离候选"：归一化后仍明显高于每一场高分记录的技能，需要核实后才能写进 `judgments.avoidable`。
- 每个维度的"计算依据"列出了用到的原始数字和判断。

## 原始事件（events）
- `--type`：damage-taken / damage-done / healing / casts / enemy-casts / buffs / debuffs / deaths / interrupts / dispels / all。
- `--player`：damage-taken、healing、buffs、debuffs 按"承受者"过滤；casts、damage-done 等按"施放者"过滤；**`all` 是双向的（施放或承受）**。`--target` 按目标名精确匹配，NPC 也可以。
- `--filter` 可写原生 WCL 表达式，例如 `type = "resurrect"`、`type = "applydebuff" and ability.id = 12345`。支持 `source.name`、`target.name`、`type`、`ability.id`、`in (...)`、`and/or`；**不支持 `target.id`**。
- 先用 `--pull N` 或 `--from/--to` 缩小窗口，再加过滤条件。带 `--filter` 的大窗口查询消耗点数较多：窗口尽量 ≤ 3 分钟；没有结果时先缩小窗口或换成 `--type` + `--player`，不要反复重试。

## 技能资料（Wowhead）
- 用英文站抓取：`https://www.wowhead.com/spell=<ID>`（中文页 `/cn/` 对自动抓取经常失败，可以用来人工核对中文名）。
- 重点读：Dispel type（能否驱散）、Duration 与 Periodic（持续时间与跳伤间隔）、Range（Self 往往表示由光环或区域触发）、是否 Private Aura、技能说明里的"frontal / cone / ground / pool"等字样。
- 新技能常常只有效果数据、没有说明文字，这时在报告里写"仅据技能效果数据推断"。

## 输出长度
- 普通命令默认最多输出 10000 字符，超出时在完整的行处截断，并给出提示。可以用 `--max-chars N` 调整（0 = 不截断），也可以缩小 `--top`、`--detail` 或时间窗口。

## 用 `query` 补充查询（高级）
需要工具没覆盖的数据时，可以直接写 GraphQL（WCL v2 client API；名称语言由 `--lang` 决定，默认中文）。
- 报告：`reportData { report(code: "X") { fights { id name keystoneLevel ... } masterData { actors { id name type subType petOwner } abilities { gameID name } } } }`
- 表格：`table(dataType: DamageDone|DamageTaken|Healing|Casts|Buffs|Debuffs|Deaths|Interrupts|Dispels|Summary, fightIDs: [N], sourceID: X, viewBy: Ability|Source|Target, startTime: T1, endTime: T2)`，返回 JSON。
- 事件：`events(dataType: ..., fightIDs: [N], startTime, endTime, hostilityType: Friendlies|Enemies, filterExpression: "...", includeResources: true, limit: 1000) { data nextPageTimestamp }`。startTime/endTime 用**报告相对**毫秒（= 战斗开始时间 + 相对时间）。`includeResources: true` 时伤害事件带 `hitPoints/maxHitPoints` 和 `classResources`（资源，如蓝量）。
- 排名：`worldData { encounter(id: E) { fightRankings(bracket: 层数-1) characterRankings(className: "Mage", specName: "Fire", metric: dps, bracket: 层数-1) } }`。
- 末尾带上 `rateLimitData { pointsSpentThisHour limitPerHour }` 可以看点数。单个表格或事件查询通常约 1 点，首次加载某报告的事件会多一些。
